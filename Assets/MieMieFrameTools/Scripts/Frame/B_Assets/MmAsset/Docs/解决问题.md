# MmAsset 解决的问题

MmAsset 主要解决资源系统中的以下问题：

```text
地址管理
依赖管理
资源缓存
Bundle 缓存
引用计数
异步请求合并
对象池
热更等待
资源加密
编辑器模拟加载
```

## 一 地址查找问题

### 问题

业务只知道：

```csharp
"UI/MainPanel.prefab"
```

但运行时需要知道：

- 资源在哪个 AssetBundle
- 资源在 Bundle 内的名称
- 资源依赖哪些其他 Bundle
- 资源属于哪个模块

如果每次加载都扫描全部配置，资源越多越慢。

### MmAsset 的解决方式

启动时读取 `BundleConfig`，建立三张索引表：

```text
CRC → BundleItem
别名 → BundleItem
BundleName → BundleItem 列表
```

`BundleItem` 保存：

```text
path
alias
crc
bundleName
assetName
dependencyList
```

加载时：

```text
资源地址
  → aliasItemDict 查询
  → 查询失败后计算 CRC
  → bundleItemDict 查询
  → 直接得到资源所在 Bundle 和依赖
```

查询复杂度接近 `O(1)`。

### 不处理会怎样

- 每次加载都要遍历配置
- 资源数量增大后加载变慢
- 业务层需要自己维护资源和 Bundle 的对应关系

## 二 依赖 Bundle 问题

### 问题

假设：

```text
MainPanel.prefab → UICommon.bundle
```

加载 `MainPanel.prefab` 时，如果只加载主 Bundle，不加载 `UICommon.bundle`，Prefab 中引用的图片、材质、字体可能丢失。

### MmAsset 的解决方式

`BundleItem.dependencyList` 保存依赖 Bundle：

```text
bundleItem.bundleName
bundleItem.dependencyList
```

加载资源时：

```text
加载主 Bundle
  → 遍历 dependencyList
  → 加载所有依赖 Bundle
  → 从主 Bundle 加载资源
```

对应代码是 `AssetBundleManager.LoadAssetBundle` 和 `LoadAssetBundleAsync`。

### 不处理会怎样

- Prefab 加载出来但引用丢失
- 材质变粉
- 图片、字体、Shader 找不到
- 运行时出现资源缺失错误

## 三 引用计数是什么

### 问题

AssetBundle 不能随便卸载。

假设：

```text
PanelA.prefab 和 PanelB.prefab
都依赖 UICommon.bundle
```

加载过程：

```text
加载 PanelA → UICommon.bundle 引用数 1
加载 PanelB → UICommon.bundle 引用数 2
```

如果 PanelA 关闭时直接卸载 `UICommon.bundle`，PanelB 仍然依赖它，就会产生资源异常。

### MmAsset 的解决方式

`AssetBundleCache` 保存：

```csharp
bundle
referenceCount
```

加载 Bundle：

```text
第一次加载 → 创建缓存 referenceCount = 1
再次加载   → referenceCount++
```

释放 Bundle：

```text
referenceCount--
referenceCount == 0 → AssetBundle.Unload()
```

资源对象本身还有：

```csharp
BundleItem.assetRefCount
```

它记录某个资源被加载了多少次。

### 不处理会怎样

直接卸载会导致：

- 仍在使用的资源失效
- 依赖资源丢失
- UI 图片消失
- 材质和 Shader 失效
- 下次使用时可能拿到无效对象

### 当前代码的两层计数

```text
资源引用计数
BundleItem.assetRefCount

Bundle 引用计数
AssetBundleCache.referenceCount
```

当前逻辑是：

```text
LoadResource
  → 资源引用数 +1
  → Bundle 引用数 +1

ReleaseAsset
  → 资源引用数 -1
  → Bundle 引用数 -1
```

当计数归零时：

```text
清理 assetObj
移除 loadedAssetDict
卸载 Bundle 和依赖
```

## 四 资源缓存问题

### 问题

同一资源被反复加载：

```text
系统A加载 MainPanel
系统B再次加载 MainPanel
```

如果每次都调用：

```csharp
AssetBundle.LoadAsset()
```

会重复查询和创建资源对象。

### MmAsset 的解决方式

`ResourceManager` 使用：

```csharp
Dictionary<uint, BundleItem> loadedAssetDict
```

加载流程：

```text
查询 loadedAssetDict
  → 已存在资源
  → 直接返回 assetObj
  → 增加 assetRefCount
```

未命中时才真正调用：

```csharp
AssetBundle.LoadAsset<T>()
```

### 不处理会怎样

- 重复加载资源
- 增加 CPU 消耗
- 产生额外内存占用
- 可能出现同一资源存在多个运行时实例

## 五 异步重复加载问题

### 问题

两个系统同时请求同一个 Bundle：

```text
系统A → 异步加载 UI.bundle
系统B → 异步加载 UI.bundle
```

如果不处理，可能启动两次：

```csharp
AssetBundle.LoadFromFileAsync("UI.bundle");
AssetBundle.LoadFromFileAsync("UI.bundle");
```

### MmAsset 的解决方式

使用：

```csharp
loadingBundleOperationDict
```

结构是：

```text
BundleKey → BundleLoadingOperation
```

第一个请求负责真正加载，后续请求发现已有任务后直接等待同一个 `UniTask`。

这叫**进行中任务合并**。

### 不处理会怎样

多个并发请求会重复发起底层 IO 和解密操作。

## 六 GameObject 重复创建问题

### 问题

频繁创建和销毁对象：

```text
打开窗口 → 创建
关闭窗口 → 销毁
再次打开 → 再创建
```

对于 UI、特效、子弹这类对象，频繁 `Instantiate/Destroy` 会产生大量 GC 和 CPU 开销。

### MmAsset 的解决方式

使用：

```csharp
Dictionary<uint, Stack<CacheObject>> objectPoolDict
```

数据结构是：

```text
预制体 CRC → 对象栈
```

释放时不销毁：

```text
GameObject
  → 放入对应 Stack
  → SetActive(false)
  → 移到 RecyclObjRoot
```

再次实例化时：

```text
Stack 有对象
  → Pop
  → SetActive(true)
  → 重新设置 Transform
```

### `CacheObject` 的作用

它不是资源本身，而是对象实例的管理记录：

```csharp
crc
path
entityId
obj
isPooled
```

`allObjectDict` 通过 `EntityId` 反查实例：

```text
GameObject → EntityId → CacheObject
```

这样 `Release(GameObject)` 可以判断这个对象是不是由 MmAsset 创建的。

## 七 热更新下载未完成问题

### 问题

资源还没下载完成，但业务已经请求实例化：

```text
请求 BattlePanel
  → 对应 Bundle 不在本地
  → 当前不能直接 LoadFromFile
```

### MmAsset 的解决方式

`readySourceDict` 保存等待任务：

```text
资源 CRC → UniTaskCompletionSource<bool>
```

流程是：

```text
资源未下载
  → 创建等待任务
  → await 挂起

下载完成
  → HotAssetsManager 发送 BundleDownloaded
  → 根据 BundleName 找到包内资源
  → 唤醒对应 CRC 的任务
  → 重新执行 InstantiateAsync
```

### 不处理会怎样

- 业务只能自己轮询文件是否存在
- 大量重复请求下载状态
- 请求顺序混乱
- 资源下载完成后还需要业务手动重试

## 八 加密资源加载问题

### 问题

普通 AssetBundle 文件可以直接被读取和复制。如果资源需要基础保护，不能直接：

```csharp
AssetBundle.LoadFromFile(path);
```

### MmAsset 的加载方式

```text
加密文件
  → AES 解密到 byte[]
  → AssetBundle.LoadFromMemory
```

优点：

- 不落地明文 Bundle
- 读取路径更安全

代价：

- 解密时存在 byte[] 内存
- 可能出现较高内存峰值
- 这不是严格意义上的流式解密

## 九 编辑器开发问题

### 问题

如果每次测试都必须先打 AssetBundle，开发效率很低。

### MmAsset 的解决方式

编辑器模式下：

```csharp
UnityEditor.AssetDatabase.LoadAssetAtPath<T>(assetPath)
```

运行时模式才走：

```text
配置表
  → AssetBundle
  → 依赖加载
  → AssetBundle.LoadAsset
```

### 不处理会怎样

- 每改一个资源都要重新打包
- 开发迭代速度慢
- 编辑器和真机需要维护两套业务代码

## 十 核心数据结构

### AssetBundleManager

```text
bundleItemDict
  CRC → BundleItem

aliasItemDict
  别名 → BundleItem

bundleItemListDict
  BundleName → 包内 BundleItem 列表

loadedBundleDict
  模块和 BundleName → AssetBundleCache

loadingBundleOperationDict
  模块和 BundleName → 进行中的加载操作
```

### ResourceManager

```text
loadedAssetDict
  CRC → 已加载资源

objectPoolDict
  预制体 CRC → 对象池

allObjectDict
  EntityId → CacheObject

readySourceDict
  资源 CRC → 等待下载完成的任务
```

## 十一 核心调用链

### 启动建表

```text
Editor模式 → 直接读取生成的 AbConfig.json
真机       → config Bundle 路径 → AES 内存解密 → LoadFromMemory
           → 读取 TextAsset(json) → RegisterBundleConfig 建立索引表
```

### 加载资源

```text
资源地址
  → alias 或 CRC 查询 BundleItem
  → loadedAssetDict 命中则返回缓存
  → 加载主 Bundle
  → 加载 dependencyList 中的依赖 Bundle
  → AssetBundle.LoadAsset
  → 写入资源缓存
```

### 实例化对象

```text
补全 prefab 后缀
  → 根据 CRC 查询对象池
  → 命中则直接取出
  → 未命中则加载 Prefab
  → Object.Instantiate
  → 写入 allObjectDict
```

## 十二 设计评价

### 设计优点

- CRC 作主键，减少字符串比较和内存占用
- 多张索引表分别服务正向查询、别名查询和反向查询
- in-flight 去重避免相同 Bundle 重复加载
- 反向索引支持下载完成后的任务唤醒
- 类对象池减少 `CacheObject` 和 `AssetBundleCache` 的 GC
- 编辑器直接使用 AssetDatabase，提升开发效率

### 当前仍需关注的问题

- 资源计数和 Bundle 计数需要严格成对释放
- `LoadAsset` 和 `ReleaseAsset` 必须由同一使用者配对调用
- 对象池会长期持有实例和资源引用，需要合理清理
- `LoadFromMemory` 解密方式会产生额外内存峰值
- 当前自研地址表工具的自动化程度还低于 Addressables

## 总结

MmAsset 解决的不是单纯的“从文件加载资源”，而是完整管理：

```text
资源地址
  → BundleItem
  → AssetBundle
  → 依赖 Bundle
  → 资源对象缓存
  → 引用计数
  → 对象实例池
  → 释放和卸载
```

真正需要 Review 的，是每个阶段的数据所有权和释放责任。
